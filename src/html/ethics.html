Ethics & privacy

Useful study tools should explain what happens to your information.

Ethical data usePrivacy & limitsImplementationReferences

Ethical data use starts with a clear purpose

Studyline is a small study task manager, not a system for assessing a student's ability or monitoring their behaviour. Its purpose is to help me organise coursework for Information Technology Systems and other subjects. A task contains a title, course code, course name, due date, description and optional notes. The application does not ask for an email address, student identifier, real account password or personal profile. I limit the information requested to what is needed to organise a task. This is a practical data minimisation decision, rather than a claim that the prototype has been certified as legally compliant.

Users retain control over what they record. They can view all saved tasks, correct inaccurate details and delete tasks they no longer need. The deletion dialogue names the selected task and offers a clear Keep task action before anything is removed. This protects against accidental loss without preventing a deliberate deletion. Past due dates are allowed: an overdue assignment is still a real responsibility, and rejecting it would make the record less accurate.

Where the information stays

Task records are stored in this browser's localStorage for this site. The application has no task server, analytics service or cloud synchronisation. Its images and other assets are included locally, so using the application does not require third-party image or font requests. This reduces unnecessary sharing, but local storage is not encryption or a private user database. Someone with access to the same browser profile can inspect the records, and other JavaScript running on the same site can access them. OWASP specifically advises against storing sensitive information in local storage.1

The login is deliberately described as a demonstration. The account details are visible in the front-end source, and the signed-in flag is held in sessionStorage. It restricts the normal task-page interface, including direct navigation to that page, but it does not provide secure authentication or separate users' data. Signing out hides the task interface; it does not erase saved tasks. On a shared device, users should remove their tasks and clear this site's browser data before leaving. Clearing browser data can also remove the only copy of their work.

Specific choices in the implementation

Validation checks the required fields, rejects whitespace-only required values, limits input lengths and checks that a due date exists in the calendar. Error messages identify the relevant field so that users can correct it. The same checks apply when updating a task. These choices support accurate records and prevent a misleading success message when a required value is missing.

Task text is inserted into the page with textContent, rather than being interpreted as HTML. A note containing markup is therefore displayed as text. This reduces the risk of script injection through task fields; it does not remove the wider limitations of a browser-only application. Labels, keyboard access, visible focus and readable error messages also matter ethically: a useful organiser should be usable without relying on colour or a mouse alone.

OWASP explains that local storage should not be treated as a protection boundary for information requiring authentication.1 For this prototype, the responsible decision is to explain its limits and avoid collecting sensitive information. A real multi-user service would need server-side authentication and authorisation, protected credential handling and a clear retention policy. I would not present this demonstration login as sufficient protection for that setting.
